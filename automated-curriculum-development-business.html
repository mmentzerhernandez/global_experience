1 - IERhub.com - Automation to First Sale

The Market Challenge

The Texas Dept. of Licensing & Regulation (TDLR) requires continuing education across 38+ regulated trades, representing a target market of nearly 1 million working professionals in Texas.

Since maintaining these licenses legally requires annual, biannual, or multi-year continuing education, it creates a potential recurring revenue stream. Currently nine different courses are scheduled to be developed, hosted, approved by TDLR, and then marketed.

How Automation Solves It

  • Consistency: each course has the same checked structure.
  • Speed: each course takes less time to develop.
  • Scale: the same process builds each new course for a new trade.

2 - Business Operations via Knowledge Management

Foundation

Records Are the Base of the Business

The business runs on its written records. Each fact has one home, and every AI session reads that home before it does any work. Decisions live in the project manifest, .claude/manifest.json. The progress of each plan lives in its plan folder, in PLAN.md and the numbered handoff files. Business knowledge lives in three levels of wikis: one main wiki, one wiki for each workstream folder, and detailed wikis for reference documents and code. A knowledge graph connects all of these files. The graph holds 6,448 items and 9,774 links between them, and a session asks the graph how one file, plan or course connects to another. Because the records hold the knowledge, a new session continues the work of the last session without a repeat explanation. The sections below show how the business uses these records to plan, run, communicate, improve and recover.

Structure

Workstream Architecture

All plans live in 10-Plans/. A plan is started there and never in a workstream folder. The diagram shows each folder that one plan moves through. A status change moves the folder.

  • Future_Plans holds approved plans that have not started. Each is one flat file named YYYY-MM-DD-topic.md. A folder inside FuturePlans is drift.
  • Current_Plans holds active work. Kickoff moves the dated file into a new folder named for its workstream and topic. Kickoff never copies. A file that remains in FuturePlans proves the kickoff was wrong. Each set folder holds one PLAN.md, the numbered handoffs, and one APPROVALS.md for gates.
  • Inactive_Plans holds paused or superseded sets. The business keeps them so a later session can see what was tried.
  • Past_Plans holds finished sets with their full plan and handoff trail.
  • Tasks holds the standing board WORK-STATUS.md, a run log, a drift report, and check-drift.sh. The board is an index only. Detail stays in each set.
  • Skill_Proposals holds the queue of proposed skill and doc changes. MIGRATION-MAP.md logs all changes.

Workflow

Session Waterfall Workflow

No session uses more than 50% of its context window. At the 50% mark, the session stops, a handoff document is written, and a new session continues the plan using that handoff document.

Folder-Based Workstreams

The workspace holds nineteen numbered folders, from 000-Dashboard to 18-RunPlan. Each folder is one workstream. Folders whose names start with _ hold what every workstream shares. The main wiki and the one-file business briefing sit at the root.

  • Archive, never delete. Superseded material moves to the owning folder's _Archive/.

Three-Tier Knowledge Base

Information is stored in tiered wikis. Tier 1 is Wiki/index.md, the main wiki. It holds navigation and governance, never operational facts. Tier 2 is one wiki per operation folder. Tier 3 is a deep wiki that organizes connections between reference documents and the code base. When two tiers disagree, the more detailed tier wins. About once a week, the operator runs /ierhub-current-state. It syncs each tier upward and rebuilds 0-HitByABus.html, the one-file briefing of the whole business.

Resilience

Operational Continuity Framework

A scheduled job mirrors the workspace into a private repository every day at 12:00, with a catch-up run after the Mac wakes. It copies only allowlisted folders. Credential folders and the payment and funnel tree appear only as a change count. A secret gate blocks any credential before it can be committed. The job renders a one-file wiki.html, writes today's date to heartbeat.txt, then commits and pushes.

  • Dead-man check. A GitHub Action opens an issue that names the successor when no commit lands for seven days.
  • Successor runbook. _Continuity/CONTINUITY.md tells a successor, an attorney, or a partner what the repository is and what to do next.

Improvement

Continuous Improvement Cycle

Every session ends by answering three questions in its handoff. What failed or surprised this session? What fact had to be re-derived that should have been recorded? What skill or doc change would have prevented it? A durable lesson becomes a feedback memory. Any implied change to a skill or a doc becomes a proposal in 10-Plans/SkillProposals/PROPOSALS.md with status proposed. No agent edits the target file directly.

  • Daily Morning Review - Approves or rejects each entry. Anything not approved stays frozen.
  • A Haiku agent applies - Each approved entry per APPLY.md. It backs up the target first and applies only the exact diff shown.
  • End of Week Review - Scores whether each change moved the metric it targeted. Two flat reviews make the change a revert candidate. The loop has run since 30 Jul 2026.

A ledger of mistakes at 13-Mistakes/mistakes.md records each real error. A session appends an entry when a lesson traces to an actual error, or when the owner names a mistake mid-session. Each entry records the symptom, the root cause, the cost, the prevention, and where the prevention now lives. An entry closes only when its prevention is codified as a feedback memory or a proposal. A session reads the ledger when it drafts a plan and during preflight. The daily brief reports the open-entry count. A monthly sweep checks every codified link and every open entry.

Stage D in Detail

CourseFactory v2: Five Stages and Three Gates

Stage D uses CourseFactory v2 to write the English text. Open the boxes under "3 - How a Course Gets Built" in the list on the left to see each stage, the checkers and the gates.

CourseFactory v2 has no single script that runs all stages. A session reads the ORCHESTRATION.md file of the course and runs each stage in order. Each checker stops when the file from the stage before it is missing. Each gate is a file on disk.

  • Entry: python3 scaffold.py --dest <path> --slug <course-slug> --modules <count>. Refuses to run if the destination exists and is non-empty.
  • Scaffold contents: copies CONTRACT.md, ORCHESTRATION.md, templates/ and tools/ into the new course directory, writes a commented course.yaml, and creates module-N/lessons/ per module plus reference/, build/, and qa/.
  • Five stages and three gates: intake, groundwork, author, package, and a closing sweep, with a gate between groundwork and author, between author and package, and between package and the sweep.

Stage 0: Intake

Per Course · Once

Intake turns a folder of raw sources into a frozen, normalized text base and a validated course configuration. It runs once per course, before any module work starts.

  • In: raw sources are dropped into each module-N/ folder, any format.
  • Out: module-N/fullsource.txt, normalized, plus a filled course.yaml.
  • Normalization: strips headers, footers, and page numbers, preserves section numbering exactly, UTF-8, one blank line between sections.
  • Configuration: course.yaml fields (title, slug, total minutes, audience, license fields) are never guessed, only asked for. Each module has one archetype: overview, changes, awareness, or procedure.
  • Exit condition: fullsource.txt frozen read-only and course.yaml validated.

Stage 1: Groundwork

Per Module · Ends at Gate 1

Groundwork turns the frozen source into a checked outline. This is where the shape of a module gets locked down before any lesson prose is written.

  • In: fullsource.txt.
  • Out: structure.md, relationships.md, outline.md, factcheck/claim-inventory.json, factcheck-verdicts.json.
  • Structure check: structure.md is a complete table-of-contents diff against the source, checked by check_structure.py.
  • Outline contract: outline.md must match CONTRACT.md §3 exactly, a time-budget table summing to the module's minutes, a Sections block citing real section IDs, an optional Infographics table. Checked by check_outline.py.
  • Claims: the claim inventory is verified by check_facts.py before the gate.

Stage 2: Author

Per Module · Ends at Gate 2

Author turns the Gate-1-approved outline into the lesson itself, then fact-checks every claim it contains before anything moves to packaging.

  • In: the Gate-1-approved outline.md.
  • Out: reference/explore-the-text.md (first module only), lessons/LESSON.md, optional infographics/, timing-stamp.json, factcheck-report.md.
  • Page rules: 150 to 450 words per page, the pattern plain restatement, workplace example, citation, a knowledge check every 3 to 5 pages, and no verbatim source text on any page.
  • Fact-checking: runs over LESSON.md unconditionally, never skipped, never sampled. Every infographic title, label, description, and value counts as a claim.
  • Copyright: non-public-domain passages get a copyright-gate pass.

Stage 3: Package

Per Module, Then per Course · Ends at Gate 3

Package converts approved lesson content into an importable Moodle LMS archive, self-checking the result before it reaches the Gate 3 review.

  • In: both gate1-approved.txt and gate2-approved.txt.
  • Out: build/module-N.mbz and build/import-checklist.md.
  • Refusal condition: build_mbz.py refuses to run without both gate files, then self-checks page counts, that every knowledge check has a correct answer, that the completion timer equals minutes times 60, and that the archive parses.
  • Mapping: each Page block becomes a Moodle LMS mod/lesson content page where Continue advances. Each Check block becomes an ungraded multichoice question page where a wrong answer returns the learner to the same page. Each module becomes one lesson activity with completion set on end reached and a completion time equal to minutes times 60. Infographics embed as plugin file images with the matching file records. The explore-the-text reference becomes an untimed resource added manually per the import checklist.
  • Not yet proven: a synthetic reference archive is the packaging base. Nobody has yet restored the archive into the Moodle LMS staging site.

Stage 4: Sweep and Filing

Per Course

The closing stage rolls up every module's fact-check history into a course-level record and hands the result for final triage, once packaging has cleared Gate 3.

  • In: all module fact-check reports plus a passed Gate 3.
  • Out: qa/course-factcheck-summary.md, qa/qa-report.md, an approval package, and qa/feedback-log.md.
  • Requirement: zero outstanding UNSUPPORTED claims across the course.
  • QA sweep: a report-only pass produces qa-report.md for triage. It blocks nothing by itself.
  • Feedback log: reviewed each renewal cycle.

The Checkers

Validate · Block or Report

Seven checker scripts run at fixed points across the five stages. A person can run each one by hand against a test module. A QA sweep at Stage 4 writes a report and blocks nothing.

  • check_structure.py (blocking): structure.md is a complete table-of-contents diff against the source.
  • check_outline.py (blocking): time budget sums exactly, mandated topics present, section IDs real.
  • check_facts.py (blocking): the retrieval-grounded claim verifier, run at Stage 1 over outline claims and Stage 2 over lesson claims. Fails on any UNSUPPORTED or CONTRADICTED verdict. NOT-IN-SOURCE and NEEDS-REVIEW go to the gate list without failing the check.
  • check_infographics.py (blocking when infographics are planned): runs the infographic pipeline and checks output against the Gate-1-approved plan.
  • stamp_timing.py: computes estimated minutes and a verdict of OK, OVER, or UNDER against budget. OVER or UNDER requires rework before Gate 2.
  • check_nonwords.py: finds words in the lesson text that do not exist, at Stage 2.
  • build_mbz.py (blocking): packaging plus the self-checks described under Stage 3.

How the Fact Checker Works

The fact checker re-execs into an isolated virtual environment, sectionizes fullsource.txt into section-aware chunks, and runs hybrid retrieval combining BM25 with dense embeddings through a parent-document retriever and an ensemble retriever, followed by a cross-encoder rerank. A state-graph cascade retrieves, applies a rerank-floor gate below which a claim goes straight to UNSUPPORTED without running natural-language inference, then a judge computes entailment and contradiction: entailment at or above 0.60 is SUPPORTED, contradiction at or above 0.60 is CONTRADICTED, anything else escalates. An escalation tier adds MiniCheck and LettuceDetect, a token-span hallucination detector, for closer review. Claims explicitly marked external skip retrieval and always return NOT-IN-SOURCE. The vector store persists per module, keyed to a corpus hash, and test and production profiles swap the embedding and reranker models. Verdict vocabulary: SUPPORTED, UNSUPPORTED, NOT-IN-SOURCE, CONTRADICTED, NEEDS-REVIEW.

The Three Gates

Decide · Sign-Off

Three gates separate the five stages. Each is a review decision that produces a file on disk, and later stages check for that file rather than trusting that review happened.

  • Gate 1, between Stage 1 and Stage 2: a person reads outline.md, the checker output, and the NOT-IN-SOURCE and NEEDS-REVIEW claim list, then decides. Approval writes module-N/gate1-approved.txt.
  • Gate 2, between Stage 2 and Stage 3: LESSON.md, the timing verdict, the fact-check summary, copyright verdicts, and any infographic renders. Approval writes module-N/gate2-approved.txt.
  • Gate 3, per course, between Stage 3 and Stage 4: the packaged archive is restored into a Moodle LMS sandbox and checked, per module, that the completion timer blocks until the declared minutes have elapsed and the lesson end is reached, that real read time is within tolerance of the timer, and that the certificate issues with license fields populated.

Each gate writes a file, and the next stage does not start without that file. build_mbz.py refuses to run unless both approval files exist. The failure table in ORCHESTRATION.md is closed: any failure that the table does not list stops the run.

4 - Compliance Engineering

How the Courses Meet TDLR Rules

TDLR sets rules before a sale, at the sale, during and after the course, and once a year. A broken rule can cost up to $5,000 for each day (Texas Occupations Code §51.302(a)). The Moodle LMS site enforces each rule in code, and it keeps a record that an auditor can read.

How the Seat Time Gate Works

Two Moodle LMS plugins share the work. local_pagedwell shows the timer and holds each page until its minimum time is met. local_seattimer sends the heartbeat and logs out an inactive learner. The server checks every request, so a change in the browser cannot open a page early. Only teachers and managers are exempt.

Runs

From a Conversation to a Plan to a Four Pane Run

  1. The operator and Claude Code talk through the work in a brainstorm session. The session asks questions until the goal, the limits and the proof of each step are clear.
  2. The session writes a plan folder. PLAN.md holds the work in numbered groups. Each item names its model, the result it must give, and a time estimate. APPROVALS.md holds the operator's answer to each decision gate. FACTS.md holds the measured facts.
  3. The /herdr-plan-run skill prepares the folder. It checks every permission, service and file that the items need, and it writes RESOURCES: PASS only when each check passes. Then it gives the operator two commands.
  4. The operator types the commands in herdr, a terminal program that shows several panes on one screen. The director script opens four panes, side by side.
PaneWhat It Does
Red: All Steps of the PlanShows every group and item with its state: done, active or queued. It shows the percent of the plan that is complete, the time left, and the time used.
Green: WorkRuns one Claude session for each group. The session does one item at a time, in plan order, and marks each item done when its check passes.
Blue: DirectorRuns the director script. It starts each Green session, waits for the handoff, checks the result files on disk, and then starts the next group.
Yellow: Decision MakerStays open for the whole run. When a run stops on a problem, the director starts one Opus session here. That session decides the next step and writes the decision to a file.
  1. Each Green session measures its own context use with a script. At 50 percent, it writes a handoff and stops. The director starts a new session from the handoff.
  2. The last item of every plan pushes the branch and opens a pull request. No session merges. The operator reviews the pull request.

Agent Rules

Limits on Helper Agents

A session can start helper agents. Without limits, a session can start too many, run them out of view, and report its own success. Two layers stop this.

  • Hard limits, set by the system. A session can start three helper agents at most, and three at a time at most. A helper cannot start a helper. Every start and every stop goes into an audit log. A session cannot change these limits.
  • Rules that each session follows. A session credits finished work only from files on disk, exit codes or the audit log. A helper's own summary is not proof. A session reports every limit that stopped it as a CEILING line. A run that ends without its expected files is a failed run.

The result is cheaper runs, smaller batches of work, and evidence that a person can check.
