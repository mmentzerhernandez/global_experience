2 - Business Operations

This panel explains how the business runs itself. It has eight stages, in order. Foundation sets one home for each fact. Structure shows where plans and workstreams live. Workflow shows how work moves from one session to the next. Execution shows how a plan runs and when it is done. Systems shows the agent rules and the knowledge base. Communication shows which emails the business sends. Improvement shows how the business learns from each session. Resilience shows what preserves the business if the operator is away.

Foundation

Single Source of Truth

Each fact has one home. No fact lives in two places. This rule stops copies from becoming different over time.

  • A decision has its home in .claude/manifest.json. The manifest holds durable facts only: decisions, paths to spec files, external state, and one pointer to the active plan. Every session reads the manifest first. A manifest longer than about 150 lines moves detail into spec files.
  • Progress has its home in the plan folder, in PLAN.md and the numbered handoffs. The manifest never tracks progress.
  • Business knowledge has its home in the wiki that owns the topic.
  • A code relationship has its home in the generated knowledge graph.
  • A retired term has its home in 10-Plans/RETIRED-TERMS.md in the same turn as the decision that retired it.

Structure

Workstream Architecture

All plans live in 10-Plans/. A plan is born there and never in a workstream folder. The diagram traces one plan through its life. A status change is a folder move and nothing else.

  • FuturePlans holds approved plans that have not started. Each is one flat file named YYYY-MM-DD-topic.md. A folder inside FuturePlans is drift.
  • CurrentPlans holds active work. Kickoff moves the dated file into a new folder named for its workstream and topic. Kickoff never copies. A file that remains in FuturePlans proves the kickoff was wrong. Each set folder holds one PLAN.md, the numbered handoffs, and one APPROVALS.md for gates.
  • InactivePlans holds paused or superseded sets. The business keeps them so a later session can see what was tried.
  • PastPlans holds finished sets with their full plan and handoff trail.
  • Tasks holds the standing board WORK-STATUS.md, a run log, a drift report, and check-drift.sh. The board is an index only. Detail stays in each set.
  • SkillProposals holds the queue of proposed skill and doc changes. MIGRATION-MAP.md logs every move.

Folder-Based Workstreams

The workspace holds seventeen numbered folders, from 000-Dashboard to 16-AdsAnalytics. Each folder is one workstream. Underscore folders hold what every workstream shares. The main wiki and the one-file business briefing sit at the root.

  • Zero-rename zones. Scheduled jobs, skills, and handoffs reach some paths by absolute path. Those paths never change. A plan set path changes only by a status move.
  • Secrets. Each folder quarantines loose secrets in its own _Credentials/. The business never uploads, syncs, publishes, or commits them.
  • Archive, never delete. Superseded material moves to the owning folder's _Archive/.
  • New folders since July 2026. 12-Diagrams, 13-Mistakes, 14-Images, and 15-OvernightRunner were added. The ads workstream moved from folder 2 to 16-AdsAnalytics. Folder 2 is now the site map and traffic funnels. Folder 8 is the legal knowledge base.

Workflow

Session Waterfall Workflow

No session uses more than half of its context window. Model quality decreases long before the hard limit. At the half mark the session stops, writes a handoff, and a fresh session continues from that file alone.

  • The checkpoint has seven steps. Finish or revert the current edit. Commit the working state. Mark completed items in PLAN.md. Write HANDOFF-N.md. Record durable decisions in the project's CLAUDE.md. Run /clear, never /compact. Answer the three lessons questions in the handoff.
  • Each handoff carries the verification command and its expected result, what is complete, the ordered remaining work, decisions and dead ends found, and the exact next step.
  • A human gate always pauses the run, at any context level. The handoff names any open gate.
  • Headless mode. A driver script can loop claude -p so each session starts fresh. There, one session equals one plan session in scope. A gate ends the session with a GATE: line, and the driver waits for the owner. The final handoff writes WATERFALL: COMPLETE. The driver refuses to run on API billing.

Execution

Plan Execution Lifecycle

Different models do different parts of the work.

  • Fable designs the architecture and writes the plan.
  • Sonnet 5 runs the waterfall. It executes the steps, writes the code, and writes the handoffs.
  • Opus 4.6 is used rarely, only at a decision fork or to judge a risk the plan did not describe.
  • Haiku does small structural edits, log cleanup, and file moves or renames.

A session with no prior context reads the manifest, then PLAN.md and the highest-numbered handoff. It runs the verification command and continues at the next step. Before Phase 1 of any plan the session runs a preflight. The preflight lists every external dependency, tests each one with a read-only call, and prints a PASS or FAIL table. A dependency that was not called is UNKNOWN, never PASS. Anything that is not PASS stops the plan.

A plan session does its tasks inline. It may dispatch one reviewer subagent that reviews the whole session diff before the handoff. Before any dispatch, the session classifies the task with one test: would a rerun give a different answer? A yes goes to an architect agent whose output must land in the manifest. A no goes to a cheaper executor agent.

An overnight runner in 15-OvernightRunner/ works a plan while the operator sleeps. It runs only tasks that are reversible, local, and verifiable. The first night on any plan is a dry run, because the owner gates the classification. It snapshots each task before it runs and restores the snapshot when verification fails. Each task gets one fresh session. It never retries, never pushes, never deploys, and never spends. The operator wakes to a morning briefing.

Completion Criteria & Quality Gates

A plan set is complete only when five things happen in one closing step. Every checkbox in PLAN.md is marked, or a dated note names each dropped item. The latest handoff carries WATERFALL: COMPLETE plus the verification command and its result. The set folder moves to PastPlans and the move is logged in MIGRATION-MAP.md. The board rows get their new paths. The manifest is updated if external state changed. Until the folder moves, the set is not complete, whatever its files claim. check-drift.sh exits non-zero when a finished set still sits in CurrentPlans.

Before the move, the session reviews the whole set for mistakes that a per-session lessons step did not capture. Each distinct mistake class gets one entry in the mistakes ledger.

  • Gates never advance without the owner. At a human checkpoint the session stops and presents the choice as options.
  • Review by default. Any change to continuity code or plugin code gets a local code review. Anything that touches auth, credentials, or the Moodle server also gets a security review. _Continuity/verify.sh must exit 0 before the work counts as done.
  • Proof over narration. After any external API write, the session reads the object back and pastes the returned id or status.

Systems

Agent Governance System

Without limits, a session can start as many helper agents as it wants, run them in the background, and report its own success. Two layers replace that with enforcement and evidence.

  1. Hard caps in settings. Three agents at once and three per session. One nested layer of helpers. No background work. Every helper is fixed to Sonnet. Every start and stop is written to an audit log. These caps live in ~/.claude/settings.json. A session cannot override them.
  2. Eight behavior rules on top. Spawn at most three helpers per prompt. No helper starts its own helpers. Wait for each helper to return before the next step. Credit finished work only against files on disk, exit codes, or the audit log, never against the helper's own summary. Take the sidecar lock before writing any shared status file. Report any limit as a CEILING line. A run that ends without its expected files is a failed run. A plan session works inline with at most one reviewer helper.

The result is cheaper runs, smaller batches, and checked evidence.

Three-Tier Knowledge Base

Information is stored at the most specific level that owns it. Tier 1 is Wiki/index.md, the main wiki. It holds navigation and governance, never an operational fact. Tier 2 is one wiki per workstream folder. Tier 3 is a deep wiki beside the code, and it is authoritative for its own domain. When two tiers disagree, the more specific tier wins. The session fixes the fact at its source. Then /ierhub-current-state syncs each Tier 2 wiki upward and rebuilds 0-HitByABus.html, the one-file briefing of the whole business.

Improvement

Continuous Improvement Cycle

Every session ends by answering three questions in its handoff. What failed or surprised this session? What fact had to be re-derived that should have been recorded? What skill or doc change would have prevented it? A durable lesson becomes a feedback memory. Any implied change to a skill or a doc becomes a proposal in 10-Plans/SkillProposals/PROPOSALS.md with status proposed. No agent edits the target file directly.

  • The owner's morning pass approves or rejects each entry. Anything not approved stays frozen.
  • An executor applies each approved entry per APPLY.md. It backs up the target first and applies only the exact diff shown.
  • A Monday review scores whether each change moved the metric it targeted. Two flat reviews make the change a revert candidate. The loop has run since 30 Jul 2026.

A mistakes ledger at 13-Mistakes/mistakes.md records each real error. A session appends an entry when a lesson traces to an actual error, or when the owner names a mistake mid-session. Each entry records the symptom, the root cause, the cost, the prevention, and where the prevention now lives. An entry closes only when its prevention is codified as a feedback memory or a proposal. A session reads the ledger when it drafts a plan and during preflight. The daily brief reports the open-entry count. A monthly sweep checks every codified link and every open entry. The first sweep is due 13 Sep 2026.

Resilience

Operational Continuity Framework

A scheduled job mirrors the workspace into a private repository every day at 12:00, with a catch-up run after the Mac wakes. It copies only allowlisted folders. Credential folders and the payment and funnel tree appear only as a change count. A secret gate blocks any credential before it can be committed. The job renders a one-file wiki.html, writes today's date to heartbeat.txt, then commits and pushes.

  • Dead-man check. A GitHub Action opens an issue that names the successor when no commit lands for seven days.
  • Successor runbook. _Continuity/CONTINUITY.md tells a successor, an attorney, or a partner what the repository is and what to do.
  • Two known traps. A scheduled script must not live under Desktop, Documents, or Downloads, because macOS blocks the job before its first line. And a session must never diagnose headless login from inside a sandboxed shell, because the sandbox returns a false expired-token error.
