1 - IERhub.com - Automation to First Sale

The Market Challenge

The Texas Dept. of Licensing & Regulation (TDLR) requires continuing education across 38+ regulated trades, representing a target market of nearly 1 million working professionals in Texas.

Since maintaining these licenses legally requires annual, biannual, or multi-year continuing education, it creates a potential recurring revenue stream. Currently nine different courses are scheduled to be developed, hosted, approved by TDLR, and then marketed.

2 - Business Operations

Folders as Workstreams

Eleven numbered folders, one per workstream. Underscore-prefixed folders hold the cross-cutting infrastructure. Some paths can never be renamed, because scheduled jobs, skills, and handoffs reach them by absolute path.



Three Tier Wiki

Information belongs at its most relevant level. In a conflict, the more specific tier always wins. Fixes are applied locally at the source, then synced upward to ensure a unified understanding across the business.



One Fact, One Home

Every fact has a single, designated place to live. By eliminating duplication across storage locations, you prevent information from diverging and contradicting itself over time.



Session Waterfall

No session runs past 50% of its context window, because LLM quality degrades long before the hard limit. Work stops cleanly before or at that mark and the handoff carries everything the next session needs, so it starts cleanly instead of inheriting bloated context.



Self Improvement Loop

Every session ends by answering three lessons questions in its handoff. Any implied skill or doc change is staged as a proposal in a queue, never applied directly. Approvals and rejections are done quickly, and approved diffs are applied by an executor agent that takes a backup first and makes the exact change only. A scheduled weekly review scores whether each change moved the metric it targeted, and flags failures for revert. Shipped 2026-07-30 in the IERhub workspace.



Subagent Governance

Without guidelines, agents can spin up as many subagents as it wanted, run them in the background, and self-report success. Three changes, applied in order, replace that scenario with documentation and verification.

  1. Hard caps, enforced by settings. Three agents at once, at most one nested layer of helpers, no background work. These are machine-enforced in ~/.claude/settings.json, not conventions, so a session cannot talk its way past them.
  2. Behavior rules on top. Each agent finishes before the next step starts. No agent spawns its own helpers. Finished work is credited only against real files on disk, exit codes, or the audit log, never against the agent's own summary. Hitting any limit is reported on a log.
  3. Routing by task type. Before dispatch, each phase is classified by one test: would rerunning it produce a different answer? If yes, then work is routed to an architect agent whose output must land in the manifest. If no, then work is routed to a cheaper executor agent.

The net effect is cheaper runs, smaller batches, and checked evidence.





How Plans are Made & Run

    • Initial Planning - Fable - Architectural design and writing of the plan.
    • Core Implemetnation of Plan - Sonnet (V5): Runs the primary waterfall workflow by executing steps, writing code, and producing handoffs for new clean context sessions.
    • Complex Decision-Making - Opus (V4.6) - Used rarely, and only at crossroads or to evaluate risks that were not expressly described during planning stage with Fable model.; avoids using V4.8 model.
    • Administrative Edits - Haiku- Manages lightweight structural edits, cleans logs, moves files or does file renaming.

    A session with no prior context reads the manifest, then the plan and the highest-numbered handoff, runs the verification script, and continues at the next step.


    What Makes a Plan Actually Finished

    A definition of "done" has four parts, all in one closing pass: every task checkbox in its respective plan is marked or the dropped items are named and dated, the latest handoff carries a completion line with the verification command and its result, the set folder is physically moved to PastPlans and logged in a migration map, and the manifest is updated if any external state changed. Until the folder move happens the set is not complete, whatever its files claim.

    Alongside the four status folders sits a Tasks folder holding a standing work-status board that indexes the active sets, a run log, and a drift report. The board is an index only: the authoritative detail stays in each set's own plan and handoff files, so one fact keeps one home.



How Plans are Organized

The diagram below traces one plan through its whole life: written as a dated file, moved into an active set folder at kickoff, worked across as many sessions as the waterfall needs, then tested against the definition of done and moved to its final home. The drift check is what makes the last step real rather than aspirational.

  • Future Plans: approved but not started, kept as flat dated files named by date and topic.
  • Current Plans: active work. Kickoff moves the dated file into a new folder named for its workstream and topic, never copies it, so a file left behind in FuturePlans is proof the kickoff was done wrong. Each set folder holds one PLAN.md, the original scope, plus the numbered handoffs the waterfall produces.
  • Inactive Plans: paused or superseded, kept rather than deleted so a later session can see what was tried and why it stopped.
  • Past Plans: finished sets, each still carrying its full plan and handoff trail as the record of how that piece of the business was built.


Which Emails Get Sent

Mapping our three disjointed email senders is essential for uncovering system gaps and understanding the actual buyer experience:

    • Stripe: Sends receipts (when toggled on).
    • Moodle LMS: Sends account and completion notifications.
    • Application: Sends staff alerts.


Continuity

A scheduled job mirrors the workspace daily into a private repository, sanitized so credential folders and the payments and funnel tree never appear beyond a change count, and a heartbeat check opens an issue if no commit lands for 7 days.

3 - How a Course Gets Built

Why sessions need scaffolding at all

An AI session has one-shot memory, which produces three failures that compound as a project grows: context drag, where the project gets re-explained every session; redundant effort, where answers already settled get re-derived; and hard amnesia, where a session's progress evaporates when it ends. Five tools answer those three problems, and course production runs on top of them.

  • Durable decisions: a manifest file holds judgment calls with their dates and reasoning, injected at session start, so a settled question stays settled.
  • Curated know-how: a hand-maintained wiki answers how something works, compiled once rather than re-derived from source documents on every question.
  • Generated structure: an auto-built graph answers how one thing connects to another across a codebase too large to hold in view at once.
  • The session waterfall: no session runs past half its context. At that mark work stops, a handoff records the verification command, what was finished, the ordered remainder, and the exact next step, and a fresh session resumes from that handoff alone. Quality degrades long before the hard limit, so the ceiling is deliberately set low.
  • A sync loop: a periodic pass re-checks the wikis against reality, so the stored knowledge is trusted because it is verified, not because it was written down once.

One fact, one home

Each of those tools owns exactly one kind of fact. Decisions live in the manifest, progress lives in the plan files, know-how lives in the wiki, and structural connections live in the graph. A fact stored in two places will eventually disagree with itself, so nothing is duplicated across homes.

One session, two models

Course production then runs as a single working session with a deliberate handover in the middle. The pattern was adopted in July 2026.

  • Plan first, on the stronger model: the session opens in plan mode. Requirements get gathered and the plan gets written before any file is touched, and the plan is approved before work starts.
  • Switch models without switching sessions: execution moves to a faster model inside the same session rather than a fresh one, so the full conversation and every decision behind the plan carry over instead of being re-derived.
  • Reserve the expensive tools for real forks: deep research runs only when a plan turns on facts outside both the repository and the model's training data. A structured decision process runs only at a genuine architectural fork. An engineering review of the plan runs when the work is large or risky. None of them run by default.
  • Why it holds: planning and execution reward different things. Separating them by mode and model, while keeping one shared context, gets the judgment of a careful planner and the throughput of a fast executor without paying for either twice.

4 - CourseFactory v2

CourseFactory v2 is deliberately not a one-command pipeline, and there is no single driver script. A course directory is scaffolded, then a session is pointed at that course's ORCHESTRATION.md, and the session is the orchestrator. Stage order is enforced by input dependencies rather than by a driver: each checker hard-fails when its predecessor's artifact is missing, and the gates that separate stages are physical files on disk, not a workflow engine's internal state.

  • Entry: python3 scaffold.py --dest <path> --slug <course-slug> --modules <count>. Refuses to run if the destination exists and is non-empty.
  • Scaffold contents: copies CONTRACT.md, ORCHESTRATION.md, templates/ and tools/ into the new course directory, writes a commented course.yaml, and creates module-N/lessons/ per module plus reference/, build/, and qa/.
  • Five stages, three gates: intake, groundwork, author, package, and a closing sweep, with a gate between groundwork and author, between author and package, and between package and the sweep.

Stage 0, intake

Per course · Once

Intake turns a folder of raw sources into a frozen, normalized text base and a validated course configuration. It runs once per course, before any module work starts.

  • In: raw sources are dropped into each module-N/ folder, any format.
  • Out: module-N/fullsource.txt, normalized, plus a filled course.yaml.
  • Normalization: strips headers, footers, and page numbers, preserves section numbering exactly, UTF-8, one blank line between sections.
  • Configuration: course.yaml fields (title, slug, total minutes, audience, license fields) are never guessed, only asked for. Each module's archetype is chosen deliberately: overview, changes, awareness, or procedure.
  • Exit condition: fullsource.txt frozen read-only and course.yaml validated.

Stage 1, groundwork

Per module · Ends at Gate 1

Groundwork turns the frozen source into a checked outline. This is where the shape of a module gets locked down before any lesson prose is written.

  • In: fullsource.txt.
  • Out: structure.md, relationships.md, outline.md, factcheck/claim-inventory.json, factcheck-verdicts.json.
  • Structure check: structure.md is a complete table-of-contents diff against the source, checked by check_structure.py.
  • Outline contract: outline.md must match CONTRACT.md §3 exactly, a time-budget table summing to the module's minutes, a Sections block citing real section IDs, an optional Infographics table. Checked by check_outline.py.
  • Claims: the claim inventory is verified by check_facts.py before the gate.

Stage 2, author

Per module · Ends at Gate 2

Author turns the Gate-1-approved outline into the lesson itself, then fact-checks every claim it contains before anything moves to packaging.

  • In: the Gate-1-approved outline.md.
  • Out: reference/explore-the-text.md (first module only), lessons/LESSON.md, optional infographics/, timing-stamp.json, factcheck-report.md.
  • Page rules: 150 to 450 words per page, the pattern plain restatement, workplace example, citation, a knowledge check every 3 to 5 pages, and no verbatim source text on any page.
  • Fact-checking: runs over LESSON.md unconditionally, never skipped, never sampled. Every infographic title, label, description, and value counts as a claim.
  • Copyright: non-public-domain passages get a copyright-gate pass.

Stage 3, package

Per module, then per course · Ends at Gate 3

Package converts approved lesson content into an importable Moodle LMS archive, self-checking the result before it reaches the Gate 3 review.

  • In: both gate1-approved.txt and gate2-approved.txt.
  • Out: build/module-N.mbz and build/import-checklist.md.
  • Refusal condition: build_mbz.py refuses to run without both gate files, then self-checks page counts, that every knowledge check has a correct answer, that the completion timer equals minutes times 60, and that the archive parses.
  • Mapping: each Page block becomes a Moodle LMS mod/lesson content page where Continue advances; each Check block becomes an ungraded multichoice question page where a wrong answer returns the learner to the same page. Each module becomes one lesson activity with completion set on end reached and a completion time equal to minutes times 60. Infographics embed as plugin file images with the matching file records. The explore-the-text reference becomes an untimed resource added manually per the import checklist.
  • Honest limitation: a synthetic reference archive is the packaging base, and Moodle LMS restore validation into the staging sandbox is still pending before first production use.

Stage 4, sweep and filing

Per course

The closing stage rolls up every module's fact-check history into a course-level record and hands the result for final triage, once packaging has cleared Gate 3.

  • In: all module fact-check reports plus a passed Gate 3.
  • Out: qa/course-factcheck-summary.md, qa/qa-report.md, an approval package, and qa/feedback-log.md.
  • Requirement: zero outstanding UNSUPPORTED claims across the course.
  • QA sweep: a report-only pass produces qa-report.md for triage; it blocks nothing by itself.
  • Feedback log: reviewed each renewal cycle.

Checkers

Validate · Block or report

Six checker CLIs run at fixed points across the five stages, each independently runnable by hand against a checked-in fixture module, plus a report-only QA sweep at Stage 4 that blocks nothing on its own.

  • check_structure.py (blocking): structure.md is a complete table-of-contents diff against the source.
  • check_outline.py (blocking): time budget sums exactly, mandated topics present, section IDs real.
  • check_facts.py (blocking): the retrieval-grounded claim verifier, run at Stage 1 over outline claims and Stage 2 over lesson claims. Fails on any UNSUPPORTED or CONTRADICTED verdict; NOT-IN-SOURCE and NEEDS-REVIEW go to the gate list without failing the check.
  • check_infographics.py (blocking when infographics are planned): runs the infographic pipeline and checks output against the Gate-1-approved plan.
  • stamp_timing.py: computes estimated minutes and a verdict of OK, OVER, or UNDER against budget. OVER or UNDER requires rework before Gate 2.
  • build_mbz.py (blocking): packaging plus the self-checks described under Stage 3.

Fact-checker architecture

The fact checker re-execs into an isolated virtual environment, sectionizes fullsource.txt into section-aware chunks, and runs hybrid retrieval combining BM25 with dense embeddings through a parent-document retriever and an ensemble retriever, followed by a cross-encoder rerank. A state-graph cascade retrieves, applies a rerank-floor gate below which a claim goes straight to UNSUPPORTED without running natural-language inference, then a judge computes entailment and contradiction: entailment at or above 0.60 is SUPPORTED, contradiction at or above 0.60 is CONTRADICTED, anything else escalates. An escalation tier adds a token-span hallucination detector for closer review. Claims explicitly marked external skip retrieval and always return NOT-IN-SOURCE. The vector store persists per module, keyed to a corpus hash, and test and production profiles swap the embedding and reranker models. Verdict vocabulary: SUPPORTED, UNSUPPORTED, NOT-IN-SOURCE, CONTRADICTED, NEEDS-REVIEW.

Gates

Decide · Sign-off

Three gates separate the five stages. Each is a review decision that produces a file on disk, and later stages check for that file rather than trusting that review happened.

  • Gate 1, between Stage 1 and Stage 2: the outline.md, checker output, the checker output, and the NOT-IN-SOURCE and NEEDS-REVIEW claim list, then decides. Approval writes module-N/gate1-approved.txt.
  • Gate 2, between Stage 2 and Stage 3: LESSON.md, the timing verdict, the fact-check summary, copyright verdicts, and any infographic renders. Approval writes module-N/gate2-approved.txt.
  • Gate 3, per course, between Stage 3 and Stage 4: the packaged archive is restored into a Moodle LMS sandbox and checked, per module, that the completion timer blocks until the declared minutes have elapsed and the lesson end is reached, that real read time is within tolerance of the timer, and that the certificate issues with license fields populated.

Gates are files on disk, not a checklist someone can skip by working faster. build_mbz.py refuses to run unless both approval files exist, so a piecemeal run of the checkers cannot substitute for a gate review. The failure-handling table in ORCHESTRATION.md is closed: anything not listed in it is a hard stop.

5 - Compliance Organization


Four Gates for Clearing Compliance

  • Before selling: CE provider registration current on fees, course approval per course and occupation, entity in good standing, background statement commitments on file. TDLR will not approve courses from a provider past due.
  • At the moment of sale: every advertisement must show the provider number and course number, a web page counts as an advertisement, no false or misleading advertising, full fee disclosure, the course must run as represented including attendance verification and seat-time enforcement, no enrolling while past due.
  • After completion, two clocks: the certificate must issue within 15 days and the completion roster must reach TDLR within 7 days. The standing tail: retain records 2 years, provide participant records within 10 days of a request, and allow unannounced auditor access where auditors never pay to enroll.
  • Annual renewal: provider registration renewal and course approval renewal before the 2027-06-22 expiry, with internal review starting 90 days prior. A lapsed registration or expired approval makes every subsequent sale unlicensed.

Penalty exposure across all four is up to $5,000 per day per violation under Texas Occupations Code §51.302(a), with each day a violation continues counted separately, plus possible revocation, suspension, or ordered consumer refunds.

Two distinct mechanisms keep gate 2 and gate 3 open

local_seattimer is the binding control that satisfies the 50-minutes-per-module requirement of §59.30(k). It measures cumulative seat time from the lesson timer rows. local_pagedwell, the per-page dwell gate live 2026-07-28, is a voluntary strengthening layer on top. It is not itself a TDLR requirement; disable it and the courses still meet the binding requirement through the seat timer.

How the dwell gate works

  • Every gated lesson page carries a required-seconds allocation, and the per-lesson sum is always exactly 3000 seconds, or 50 minutes. Verified across all 8 gated lessons on 2026-07-28.
  • A client-side widget beats the server about every 30 seconds, but only while the tab is focused, visible, and has seen activity since the last beat. The server computes the credit itself as the smaller of the gap since the last beat and a 75-second grace cap, bounded absolutely by the time since first view. The client never sends a duration and the server never trusts one. Over-credit is structurally impossible rather than merely unobserved.
  • Enforcement runs server-side on every request through the Moodle LMS after_config hook, independent of JavaScript. A learner who strips the disabled attribute off a button in devtools is still refused.
  • Exemption is capability-based and granted only to editing-teacher and manager archetypes. The TDLR auditor role is deliberately not exempt and is gated exactly like a student, so an auditor walkthrough produces the same evidence trail a real learner's would.
  • English and Spanish are page-for-page identical in page count and per-page split, each totalling 3000 seconds. Two orientation lessons are deliberately excluded and carry no CE credit.

Measured accrual behavior

The rate investigation closed 2026-07-27: active reading credits at 0.85 to 1.0 times wall clock and never above; passive idle with no requests credits zero; returning after idle credits exactly the 75-second grace, with a clawback that moves the start time forward to strip anything beyond it; two concurrent browser tabs credit 1.0 times, not 2.0, measured directly rather than reasoned about. Both defects found were under-credit only, never over-credit.

6 - Delivery Platform

A self-hosted Moodle LMS instance at start.ierhub.com delivers the approved course and is the system of record for completions and the two-year retention requirement. Two courses run on it, English and Spanish.

  • Payment: Stripe checkout is the system of record for who bought what and when. English has a webhook-driven enrollment path. Spanish currently has no fee enrollment row and cannot be sold through the self-service path yet; a Spanish checkout flow is in progress but not shipped.
  • Certificate mailing: Certificates print and mail through mailing integration.
